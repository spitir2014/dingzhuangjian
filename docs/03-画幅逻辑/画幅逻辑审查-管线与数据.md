## 结论速览（最严重的 6 条）

1. 内容段「一份」是硬架构：compilePrompt 只遍历 state.blocks 一个数组，块文本只能全局改；目前唯一能按画幅差异化的是 4 个结构段的文字（templateText）、新增的 layout.vars（变量取值覆盖）、layout.suppress（整段不拼）和 layout.orient（比例约束）。块文本、块顺序、单块启停仍无法按画幅改写。
2. data/templates.json 与 data/layouts.json 快照时逐对象完全一致（整对象 deep equal 为 true），但运行时以 layouts.json 为准，两份靠手工同步。01:08 后 validate 增加了漂移 console.warn，但它不改变退出码（仍是绿灯），且只比较 orient/structure/vars/suppress、不比较 label；只改一份时 npm test 仍可能通过，而界面/出图用的是 layouts 的旧数据。
3. localStorage.templateText 缓存结构段文本，applyTemplateStructure 优先使用缓存（keep.text 优先于 data）。data 文案更新后，只要用户曾在某个画幅上编辑/开关/拖拽过任意块，或点过「简洁/标准/详细」「画幅预设」「切换画幅」「新建画幅」，该画幅的 4 段结构文本就被缓存，新文案不会生效。新增的 LEGACY_STRUCT 迁移只在「缓存文本与旧默认一字不差」时才摘掉缓存，部分手改与中间版本无法迁移（详见 4.6/4.7）。
4. 内容段文字、块顺序、自定义段只存在浏览器 localStorage；layouts.json 不保存任何内容段文本。换浏览器、清站点数据、隐私模式就会丢；saveState 静默吞掉写失败（配额/禁用），刷新后全部回默认且无提示。
5. 校验仍有结构缺口：templates↔layouts 无 diff 检查、presets.layoutId 只按 templates 校验、LAYOUT_ORIENT 仍是硬编码 5 个 id（与新的 orient 字段并行存在）、结构段文案与内容段之间的自相矛盾无检查、内容段「每段是否被某个画幅用到」无检查。validate 通过不等于运行时数据正确。
6. 生成请求的 prompt 由前端 compilePrompt 生成后原样发给上游，服务端不加工不截断。存档 JSON 在 01:04 快照时不含 prompt；01:08 后已改为 schemaVersion 3，写入 prompt/promptHash/promptMeta（仍缺 structure/vars/suppress 快照与数据版本，旧存档仍是 schemaVersion 2）。失败重试仍用内存里旧 job 快照（含旧 providerId），刷新即丢。

## 1. 拼装链路

### 1.1 state.blocks 从哪里来（启动时序）

结论：state.blocks 是运行时唯一真正的「提示词块列表」。它的初始化只发生一次，文本来自 data 的快照；之后与 data 文件脱钩，只跟随 localStorage 与界面编辑。

证据：

- 加载数据：web/app.js:84-111
    - DATA.order / DATA.content 来自 /data/templates.json（100-101 行）
    - DATA.layouts 优先用 /api/layouts 返回的 layouts，否则回退 templates.templates（102-106 行）
    - DATA.presets 来自 /data/presets.json（106 行）
- 恢复本地状态：restoreState（137-160）→ restoreBlocks（189-208）
    - 有 localStorage.blocks 时直接使用（192-195）
    - 只有旧版 blocksByTemplate 时走迁移并合并内容段（197-207；迁移函数 166-187）
- 启动装配：boot（3753-3767）
    - restoreState 成功后调用 loadBlocks（3761）
    - fillStaticSelects（3547）里再调用 normalizeTemplate / renderTemplateOptions / loadBlocks / renderBlocks（3550 附近）
- loadBlocks（1667-1674）：
    - state.blocks 为空才 defaultBlocks（1668）
    - migrateLegacyContent / migrateLegacyStructure（1669-1670）
    - ensureBlockSkeleton 补缺段（1671）
    - detailPreset 非 custom 时 applyDetailPresetFlags（1672）
    - applyTemplateStructure 铺当前画幅结构段（1673）
- defaultBlocks（1567-1577）：按 DATA.order 逐项生成；内容段取 DATA.content[id] 的 label/text/enabledDefault；结构段取 currentTemplate().structure[id] 的 label/text，默认 enabled true。

后果：data/templates.json 的 content 文案只在「首次生成 blocks」时进入 state.blocks；刷新时如果 localStorage 有 blocks，就以 localStorage 为准（迁移只处理登记过的旧文案）。data 改动不能刷新已有用户的块文本。

### 1.2 compilePrompt 的过滤与拼接规则

结论：compilePrompt 只做 5 件事：按 state.blocks 顺序取块、过滤 enabled、过滤当前画幅 suppress、单次变量替换、trim 后丢掉空块、以空行连接。没有去重、没有按画幅重排、没有长度限制、没有 unknown 变量阻断。

证据：

- web/app.js:495-503
    - 498：filter(b.enabled && !isBlockSuppressed(b.id))
    - 499：compileBlockText（489-493，单次正则替换 {{key}}，unknown 原样保留）
    - 500-501：trim 后丢弃空文本
    - 502：join 两个换行
- buildVars（415-487）提供变量：
    - 参数值/Phrase（417-429；选择型第二遍再覆盖为 phrase，472-479）
    - 特殊变量 aspectText / sizePx / underTop / outfitExtra / name / profileText / signatureSentence（430-471）
    - 最后叠加当前画幅 vars（480-486），只接受字符串值
- 段落「不要出现」不是独立的 negative prompt 字段，只是 state.blocks 里的普通块，和其他段落一起拼进同一个 prompt（data/templates.json:3-24 的 order 里 negative 只是普通 id）。
- 「最终提示词」预览与 copyPrompt 用的也是 compilePrompt（updatePromptPreview 2074 行计算长度；copyPrompt 在 bindUI 内），但预览 HTML 另有一份内联实现（2063-2067）和一个未被调用的 compilePromptHTML（661-668），三处逻辑重复，任何拼装规则变更都必须同步改三处。

后果：布局/内容差异只能通过「换文本」实现；同一内容段在所有画幅里的文字完全一致（除 vars 值替换）。前缀、后缀、顺序都没有画幅维度。

### 1.3 块顺序定义在哪些数组里

结论：运行时顺序由 state.blocks 的数组顺序决定，初始顺序由 data/templates.json 的 order 决定；layouts.json 不保存顺序；拖拽只改 state.blocks（localStorage）。

证据：

- data/templates.json:3-24：order 共 20 项 = 4 个结构段（format/layout/style/negative）+ 16 个内容段。
- defaultBlocks（app.js:1567-1577）按 order map 生成初始数组。
- ensureBlockSkeleton（1606-1622 附近）按 DATA.order 的索引插入缺失段：Math.min(i, blocks.length)，如果用户拖拽过，插入位置可能不在相邻段旁。
- renderBlocks 的 drop 处理（2027-2034）：splice 改 state.blocks 顺序后 persistBlocks。
- compilePrompt 不排序，直接按数组顺序输出（497-502）。
- layouts.json 顶层只有 version / layouts，layout 对象只有 id/label/structure/vars/suppress/orient（data/layouts.json:1-139；server saveLayouts 152-154 只写 {version, layouts}），没有 order 字段。

后果：某画幅想把「左上角文字」挪到中间或末尾，只能全局拖拽，所有画幅一起变；suppress 只能整段删，不能换位置。

### 1.4 「人物内容段一份、所有画幅共用」的具体后果

结论：共用一份内容段 + 4 段结构段，只覆盖了「版式描述」的差异；人物描述、表情、服装、文字位置这些真正与画幅强相关的内容无法按画幅改写。三种典型诉求的现状：

| 诉求 | 现在能做到什么 | 为什么做不到（证据） |
| --- | --- | --- |
| 九宫格要九种表情 | 用 layout.vars 覆盖 expression/intensity/gaze，把「单一表情」换成「按版面段的九格清单执行」（data/layouts.json:119-124、templates.json:218-224）；版面段自己列九条表情（data/templates.json:208） | 内容段仍是全局一份：expression 段的文字「表情：{{expression}}。{{intensity}}。{{gaze}}。」（templates.json:50-53）只能靠覆盖变量值改写，不能按画幅替换整段句式；左栏「表情」参数在该画幅被静默无视；记忆点句子在 vars 覆盖之前就用原参数生成（app.js:455-471 先于 480-486），可能仍写着「表情平静」，与九格清单矛盾 |
| 半身像想关掉腿部/下身描述 | 目前只有 portrait 用 vars.outfitExtra 覆盖「下身只穿短裤」这一句（data/layouts.json:101-103）；可再用 suppress 整段隐藏，但会连体量/比例一起没了 | 体量段（templates.json:30-33）包含 legRatio；比例段（62-65）包含 legShape/waistline；这些是同一段文本里的多个变量，没有「本画幅删掉某几个子句」的机制。suppress 是整段级（app.js:1532-1534），vars 只换值不删句，改文本则全局生效 |
| 某画幅想把文字挪到别处 | 只能 suppress「左上角文字」整段（如 expression_grid，data/layouts.json:132-134），或全局修改 info 段文字/位置（templates.json:58-61） | info 是全局内容段，文本、顺序、开关都是共用的；没有 per-layout 文本/顺序覆盖。且结构段 negative 文案写死了「左上角那行人物信息」（如 templates.json:110），一旦别处 suppress info，negative 就自相矛盾 |

补充后果（同样重要）：

- 左栏参数「未用」标记只反映 enabled/suppress（usedVarKeys 570-577；updateParamUsage 746-766），不反映 layout.vars 覆盖：expression/gaze 在九宫格/正背卡/三视图里被覆盖，参数行仍显示「已用」，用户改它没有任何效果也无提示（4.8 详述）。
- 结构段本身也受「一份 state.blocks」影响：拖拽顺序全局生效；结构段 enabled 按画幅记（templateText），内容段 enabled 全局共享。
- 自定义段（kind=free）同样全局共用（README 107 行也这么写），无法做成某画幅专属。

建议：在现有 vars/suppress 之上增加 per-layout 的「内容段覆盖」数据结构（第 7 节给最小改法）：允许某画幅覆盖指定内容段的 text/enabled，同时保留 vars 作为变量值覆盖、suppress 作为整段关闭。三者优先级建议：suppress > content[blockId].enabled > 全局 enabled；content[blockId].text > 全局 text。

## 2. 数据一致性

### 2.1 templates.json 与 layouts.json 的逐段 diff（快照时刻：无漂移）

结论：快照时刻两份文件的 5 个画幅对象 deep equal 为 true，逐段文本一致；但这完全依赖手工同步，没有任何自动检查。两者版本字段也不一致（templates version 4，layouts version 1）且运行时都不校验版本。

证据（tmp/audit-deep.mjs、tmp/audit-diff.mjs 的运行结果，只读）：

- 整对象比较：sheet_2view / sheet_3view / fullbody / portrait / expression_grid 全部 identical: true；两份文件 ids 顺序相同，都是 5 个。
- 每个 layout 的字段：id、label、structure、vars（部分）、suppress（仅 grid）、orient（5 个都有）。
- 逐段文本长度（templates 与 layouts 完全一致）：

| 画幅 | format | style | negative | layout |
| --- | --- | --- | --- | --- |
| sheet_2view | 64 | 94 | 271 | 486 |
| sheet_3view | 64 | 94 | 290 | 484 |
| fullbody | 58 | 67 | 205 | 284 |
| portrait | 58 | 67 | 222 | 276 |
| expression_grid | 58 | 76 | 148 | 490 |

- 跨画幅差异：format 有 2 种（两个多视图 64 字，其余 58 字）；style 有 4 种；negative 5 种全不同；layout 5 种全不同。说明这些差异是人手维护的，不是模板生成。
- 版本：templates.json:2 为 4；layouts.json:2 为 1；server saveLayouts 固定写入 version:1（server.mjs:152-154）；validate 只检查 params.version（validate-data.mjs:17）。

后果：

- 改一份忘改另一份时没有任何报错；运行时 DATA.layouts 取的是 /api/layouts → server loadLayouts 优先读 layouts.json（server.mjs:144-150），templates.templates 只是回退。因此「只改 templates.json」在正常运行时完全不生效。
- validate 现在虽然两份都校验（validate-data.mjs:153-159），但只是各自自洽，不做相等性比较；check-prompt 优先用 layouts.json（check-prompt.mjs:12-16），也会掩盖 templates 的差异。
- version 字段没有消费方：app 不检查模板版本，server 硬编码 1，validate 不检查 templates/layouts 版本。升级行为只能靠 LEGACY_* 常量手工登记。

建议：

1. validate 增加 templates.templates 与 layouts.layouts 的逐 id 对比（id 集合、label、structure 四段 text、vars、suppress、orient 深比较）；不一致直接 fail 并指出差异字段。
2. 统一版本来源：layouts.json 写入 templates.version（或 templates 加 layoutsVersion），app 加载时校验；或者干脆让 layouts.json 成为唯一运行时数据，templates.json 只保留 content/order 与出厂快照，并提供「同步出厂画幅」脚本。
3. 短期至少加一个 npm script（如 data:diff）给 CI 手动跑；在 README 写明「改画幅文案必须两份一起改，否则运行时用 layouts」。

### 2.2 server 的 loadLayouts / saveLayouts / cleanLayout 会丢什么

结论（快照时刻）：cleanLayout 已保留 vars/suppress/orient（server.mjs:156-183），但仍是白名单清洗：structure 只保留 4 个 LAYOUT_KEYS（135 行）、未知顶层字段一律丢弃、标签截断 24 字、vars 键 40/值 4000、suppress 最多 24 个；saveLayouts 只写 {version:1, layouts}。因此通过 UI 的写操作会静默丢掉文件里手工加的其它字段，以及任何不在白名单里的结构段。

证据与操作矩阵：

| 操作 | 代码 | 是否写文件 | 会丢/会变什么 |
| --- | --- | --- | --- |
| GET /api/layouts | server.mjs:1162-1163；loadLayouts 144-150 | 否 | 无。但 JSON 解析失败或 layouts 为空时静默回退 templates.templates，不报错、不备份 |
| POST /api/layouts（新建/改名/未来编辑） | 1168-1176；cleanLayout 156-183 | 是，整份重写 | 该画幅顶层非白名单字段（如未来的 content/order/note/updatedAt 等）全部丢弃；structure 里非 format/layout/style/negative 的键丢弃；vars 非字符串值/超长、suppress 非字符串/超长丢弃；label、structure.label 截断 24 字；orient 只接受四种枚举（166） |
| DELETE /api/layouts | 1177-1186 | 是，整份重写 | 删除目标画幅；其余画幅对象原样写回，但文件顶层被 saveLayouts 重写为 {version:1,layouts}，顶层扩展字段丢 |
| POST /api/layouts/reset | 1163-1166（unlink） | 删除整个文件 | 所有画幅（含 vars/suppress/orient/自定义画幅）全部消失，回退 templates.templates |
| 手工编辑 layouts.json | 不经过 server | 否 | 字段可以先存在（GET 原样返回），但下一次任一写操作会按上表清洗；app 只消费 id/label/structure/vars/suppress/orient |

还有一个「validate 允许、server 会丢」的错位：checkLayoutList 允许 structure 里出现 content id（validate-data.mjs:124-125），而 cleanLayout 只保留 4 个 LAYOUT_KEYS（server.mjs:159-163），app 的 applyTemplateStructure 也跳过 content id（app.js:1593-1594）。也就是说手工把内容段写进 structure 可以通过校验，但在改名/新建时被服务端丢弃、运行时也不会应用——三处行为不一致。

另外：cleanLayout 不校验 structure 文本非空（只 String(s.text||"")），API 可以写入空结构段；validate 才会报「缺结构段」。cleanLayout 也不校验 id 格式/长度/重复（重复由调用方 findIndex 处理），POST 可以用任意 id。orientation 白名单是后加的（166），说明白名单模式本身会让新字段默认丢——每加一个字段都要改 cleanLayout + validate，这是 double-source 架构的持续成本。

### 2.3 UI 存块的路径：localStorage vs layouts.json

结论：UI 只把「画幅列表/结构段默认文本/vars/suppress/orient」写进服务端 layouts.json；所有块文本（内容段+结构段编辑结果）、块开关、块顺序、自定义段只在 localStorage。两者没有版本/时间戳，互相覆盖时以 localStorage.templateText 优先。

localStorage（key 见 app.js:26 = zaoxiangtai.v1）存什么（saveState 114-135）：

- providerId / modelId / ratio / res / batch / quality / showPhrases / templateId / params / locks / seed / meta / highlights / detailPreset / collapsedGroups
- blocks：全部块的 {id, kind, label, text, enabled} 数组，顺序即提示词顺序（内容段文本、结构段文本快照、自定义段都在这里）
- templateText：按画幅 id → { format/layout/style/negative: {text, enabled} } 的结构段缓存（133 行）

layouts.json 存什么（data/layouts.json；server cleanLayout）：

- 画幅列表：id / label / structure（4 段 label+text）/ vars / suppress / orient
- 不保存：任何内容段文本、块顺序、自定义段、detailPreset、用户对结构段的编辑（结构段编辑只进 localStorage.templateText，永远不会 POST 到 layouts.json）

哪些改动会丢（按丢失机制）：

| 改动 | 存在哪 | 丢失条件 |
| --- | --- | --- |
| 内容段文字/开关/顺序/自定义段 | localStorage.blocks | 清站点数据、换浏览器/隐私窗口、配额满或禁用 localStorage（saveState catch 空实现，app.js:135）、点「重置」按钮（3342 附近清 blocks/templateText） |
| 结构段文字/开关 | localStorage.templateText（也复制在 blocks 里） | 同上；执行「恢复默认画幅」（resetLayouts 1929 行清 templateText + server 删 layouts.json）；被 data 新文案更新遮住（4.4/4.6） |
| 画幅列表/名称/structure 默认文本/vars/suppress/orient | data/layouts.json | 恢复默认画幅（删文件）；cleanLayout 白名单清洗；服务端写失败（POST 返回错误时客户端不改本地 DATA.layouts，但文件可能已被写一半？saveLayouts 直接 writeFile，无原子写/备份） |
| templateId/ratio/res/detailPreset 等 | localStorage | 清缓存；templateId 指向已删画幅时 normalizeTemplate 会切到第一个（1683-1688） |
| 已生成提示词 | 不存（见 6.2） | 无法恢复 |

补充：唯一能让界面上的结构段编辑间接进入 layouts.json 的路径是「新建画幅」——structurePayload 复制屏幕上现有 4 段文字（app.js:1827-1839，createLayout 1842-1845）。也就是说，用户在 A 画幅改的结构段文字，会随「新建画幅」被固化成新画幅的 structure。除此之外，结构段编辑不会被服务端持久化。

### 2.4 建议（数据一致性）

1. 用一个数据源：layouts.json 作为唯一运行时画幅数据，templates.json 只保留 content/order 与出厂画幅快照；启动时若两份画幅不一致，在状态栏/toast 报警（而不是静默用 layouts）。
2. 服务端写 layouts.json 改为「读-改-写 + 原子写」（tmp 文件 + rename），并在写前保留一个 .bak；cleanLayout 只清洗用户可编辑字段，其余字段原样透传（或改为 schema 校验而不是白名单）。
3. localStorage 增加数据版本戳（templates.version + layouts hash）；版本变化时对 templateText 做差异清理（见 4.9）。
4. README 更正「界面改完整份列表落到 layouts.json」的说法：只有画幅管理操作会写 layouts.json，块文本编辑只写浏览器。

### 4.2 applyTemplateStructure 会覆盖什么

证据：app.js:1590-1603。

- 遍历 state.blocks；只处理「不是内容段、且当前画幅 structure 里存在该 id」的块（1593-1594）。
- 设置 kind=structure、label=data label、text：有 templateText 缓存则用 keep.text，否则用 data 的 s.text（1597-1599）。
- enabled：仅当缓存有 boolean 时才取缓存（1600），否则保留内存值。
- 最后调用 ensureRatioForTemplate（1602，新加）——它会根据 currentTemplate().orient 检查当前 ratio，不合法时自动切到第一个可用比例并 toast（1552-1561）。

不覆盖：内容段、自定义段、块顺序、vars/suppress（这两者在编译时实时读）、结构段的删除（不存在的块不会补，补缺由 ensureBlockSkeleton 负责）。

风险：

1. 缓存优先（1599）：data 文案更新永远输给 templateText 缓存（详见 4.6）。
2. 若当前画幅缺某个结构 key（手工数据/服务端空壳），1594 直接跳过，state.blocks 会保留上一个画幅的文本（跨画幅串味）。validate 现在能发现缺段，但运行时没有防御。
3. ensureRatioForTemplate 使 applyTemplateStructure 带副作用（改 ratio + saveState + toast）。它会在 boot、切换画幅、预设、改名/删除当前画幅、恢复旧人物后都可能触发；开机时如果 localStorage 里 ratio 与当前画幅 orient 不兼容，会自动改比例并弹 toast——这是有意的，但会让「刷新后比例变了」看起来像 bug。

### 4.3 ensureBlockSkeleton 何时插入

证据：app.js:1606-1622 附近；调用点只有 loadBlocks（1671）、resetBlocks（3375 附近，点「重置」）、以及 boot 两次 loadBlocks（3761、fillStaticSelects 3550 附近）。

- 缺段按 DATA.order 的索引 i 插入到 Math.min(i, blocks.length) 位置；有自定义拖拽顺序时可能不贴邻。
- 只补不删：data 删除的内容段不会被移除；data 新增的段会在刷新后补，enabled 取 enabledDefault（内容段）或 true（结构段）。
- 缓存/迁移执行顺序：defaultBlocks → migrateLegacyContent → migrateLegacyStructure → ensureBlockSkeleton → detailPreset flags → applyTemplateStructure（1667-1674）。即：新段会先被 detailPreset 覆盖开关，再铺结构段。

### 4.4 「改了不生效 / 换画幅丢改动 / 刷新回默认」路径清单

P1【最严重，data 改了不生效】templateText 缓存优先。stashTemplateStructure 在任意 persist 时把当前画幅 4 个结构段全量写入 localStorage（1580-1587）；applyTemplateStructure 读取时 keep.text 优先于 data（1595-1599）。触发缓存的最小动作包括：点一次「简洁/标准/详细」（applyDetailPreset→persistBlocks，1265）、点一次画幅预设（1779）、切换一次画幅（3522）、新建画幅（1842），甚至不需要改任何文字。之后 data 的 layout 文案更新对这台浏览器无效。证据链：1252-1270、1773-1793、3521-3530、1841-1858、1580-1603。

P2【templates 改了不生效】运行时 DATA.layouts 来自 /api/layouts（loadData 102-106；server loadLayouts 144-150）；templates.templates 只是回退。只改 templates.json 的 templates 数组没有任何效果；但 content/order 仍从 templates 读（loadData 98-101），所以「改内容段文字」会生效（对没有本地覆盖的段），「改画幅结构段」不会——容易误判。

P3【layouts.json 手改不生效（当前会话）】DATA.layouts 只在 boot 的 loadData 与 layout POST 后更新（applyLayoutsResponse 1815-1824）；没有文件监听、没有轮询。手改文件后必须刷新，或在界面上做一次画幅管理操作触发响应替换。

P4【内容段改一次全画幅生效】这是设计（1.4），但用户想要「只改半身像的体量段」时，唯一手段是 suppress 整段或改全局；layout.vars 只能换值不能改句式。

P5【layout.vars 覆盖左栏参数，但 UI 不提示】（01:15 后已缓解）usedVarKeys（570-577）、updateParamUsage（746-766）、offHint（739-744）只看 enabled+suppress；expression/gaze 在 sheet_2view/sheet_3view/expression_grid 被 vars 覆盖后，左栏仍显示「已用」。Lead ⑦ 已在 offHint/参数详情里标注 suppress 与 vars 覆盖（app.js:740 附近），所以「为什么改了没效果」现在能找到说明；剩余问题是左下参数行仍不能直接编辑/跳转 vars，属于体验优化。

P6【记忆点/人物档案与 vars 覆盖矛盾】profileText/signatureSentence 在 455-471 由原始参数生成，vars 覆盖在 480-486 之后才叠加。若覆盖 expression/identity 等，档案句/记忆点句仍是旧值，提示词内部自相矛盾。

P7【vars 值不递归编译】compileBlockText 只做一次替换（489-493），buildVars 直接把 vars 字符串塞进变量表（480-486）。若 data 的 vars 值里写了 {{x}}，它会原样进入 prompt；validate 不扫描 vars 值。

P8【刷新后内容段开关回默认（特定条件）】applyDetailPresetFlags 每次 loadBlocks 都按 detailPreset 重置 detailFace/detailBody/profile/signature 的 enabled（1252-1258、1672）。正常界面 toggle 会 markDetailCustom（1987、1239-1244）避免此问题；但旧 localStorage、手工改 detailPreset、或未经 toggle 的程序化改动，会让刷新回到预设档位。

P9【旧内容段文字不被 data 更新覆盖】blocks 文本存在 localStorage（saveState 132）；migrateLegacyContent 只对 outfit/info 且必须与 LEGACY_CONTENT 完全一致才替换（1625-1635）。其它内容段以后改文案没有迁移机制。

P10【data 删除内容段后旧 blocks 仍保留】ensureBlockSkeleton 只补不删（1606-1622）；compilePrompt 只读 state.blocks（495-503）。data 删掉的内容段仍会进入该用户提示词，validate 也看不到 localStorage。

P11【saveState 静默失败】saveState catch 为空（135）：localStorage 满、隐私模式、被禁用时，所有块/结构文本/设置都只存在内存，刷新即丢，且没有任何提示。

P12【删除画幅后缓存残留 / 同 id 复活旧缓存】（01:15 后已修）Lead ⑤ 已在 deleteLayout 里清掉对应的 state.templateText（app.js:1890 附近）；restoreBlocks 仍会恢复其他画幅的 legacy templateText，这是预期行为。剩余风险只在于「手工把 layouts.json 里已删画幅的 id 再建回来」时旧缓存是否还有别的副本。

P13【恢复默认画幅丢弃结构编辑与自定义画幅】resetLayouts 会删 layouts.json、清 templateText、blocks=defaultBlocks 仅保留内容段 text/enabled + 自定义段追加（1910-1944）。确认框有说明，但没有导出/备份入口。

P14【normalizeTemplate 切画幅但不重绘】1683-1688 在 templateId 失效时切换并 applyTemplateStructure，但没有 renderBlocks/renderParams/updatePromptPreview；当前只在 fillStaticSelects 调用（3547），后面紧接着 loadBlocks/renderBlocks 兜底。若未来在其它地方调用，会出现「下拉框显示旧画幅、提示词已是新画幅」的不一致。

P15【画幅切换时 renderBlocks 是否一定重绘】四条用户路径都重绘：templateSel 3521-3530、applyPreset 1773-1793、createLayout 1841-1858、deleteLayout 1881-1908；boot 恢复旧人物 3785-3789 也重绘。但 applyLayoutsResponse 本身只更新 DATA.layouts + renderLayoutList + renderTemplateOptions（1815-1824），不重绘 blocks；改名/删除当前画幅时由调用方补 renderBlocks。这是一条隐性契约，新增入口需要记得补。

P16【比例与画幅方向】（01:15 后已修兜底）renderSizeControls 会禁用与 orient 不兼容的比例（921-940）；Lead ⑥ 已在 applyPreset 里加方向兜底（app.js:1780 附近），冲突时不再强行写入非法比例。validate 也会拦 preset 与 orient 的冲突（246-249），但仍是「数据正确 + 运行时兜底」双保险，不是单一来源。

P17【vars/suppress/orient 只读 DATA.layouts】buildVars 481-486、templateSuppressedIds 1528-1531、templateOrient 1544-1547 都读内存 DATA.layouts；手改 layouts.json 要刷新；UI 不能编辑 vars/suppress/orient，只能文件编辑+刷新（README 169-176 已说明字段语义，但没给 UI）。

P18【suppress 可写结构段 id】（01:15 后已修）app 的 isBlockSuppressed 现在明确「只有内容段可以被画幅停用」（app.js:1538-1541），手改 data 把 format 写进 suppress 也不会丢结构段；validate 只允许 content id（143-150）。剩余：server cleanLayout 仍只是过滤字符串（不校验 id 属于内容段），但服务端写入后 app 会忽略、validate 会报，属于低风险。

P19【未用标记与 suppress 的提示语】updateParamUsage 用 usedVarKeys（含 suppress 过滤）；若某参数只在被 suppress 的段出现，会标「未用」。01:08 后 offHint 已加「本画幅…版面停用了这一段」分支（app.js:740），这一项已基本修好；剩余问题只是「被 layout.vars 覆盖」仍不显示（见 P5）。

P20【vars 可覆盖画布/元变量】buildVars 对 vars 的 key 没有种类限制（480-486）；validate 只要求可解析（134-141）。因此画幅可以在 vars 里改 aspectText/name 等，和顶栏/人物档案显示不一致，且没有提示。

P21【校验与用户实际提示词脱节】validate/check 只看 data 文件，看不到 localStorage 的 blocks/templateText；绿灯不代表用户实际出图 prompt 正确（P1/P9/P10/P11 都属此类）。

P22【data 文件和 Web 资源无需强刷】server 的 /data 与静态资源都带 Cache-Control: no-store（server.mjs:1086-1087、1233），刷新就能拿到最新文件；所以「刷新还是旧文案」几乎都是 localStorage 缓存（P1），不是浏览器 HTTP 缓存。

### 4.5 applyDetailPresetFlags 与 applyTemplateStructure 的调用先后

结论：loadBlocks 里的顺序是 ensureBlockSkeleton → applyDetailPresetFlags → applyTemplateStructure（1667-1674）。当前两者作用集合不相交：DETAIL_PRESETS 的 key 都是内容段（1246-1250），applyTemplateStructure 只处理结构段（1593-1594），所以先后目前没有功能冲突。

风险与建议：

- 这是「靠 id 不重叠」维持的安全，不是设计保证。若以后把某个结构段 id 放进 DETAIL_PRESETS，applyTemplateStructure 会在 flags 之后把它覆盖回 keep.enabled/data enabled，预设对这段失效；反过来若把内容段 id 放进 structure，也会混乱。
- 更稳的顺序：ensureSkeleton → applyTemplateStructure → 仅当「首次生成 blocks」或用户显式点预设时 applyDetailPresetFlags；不要每次 load 都重置 content enabled。
- 另注意 applyDetailPreset 会 persistBlocks（1265），从而 stash 结构段（自动写缓存）——预设操作与结构段缓存耦合（P1 的来源之一）。

### 4.6 templateText 的写入路径：哪些「不需要编辑文字」的操作也会写缓存（回应 Lead 问题 1）

结论：boot 的常规路径没有隐性 stash/persist；但四类「纯切换/预设」操作会在用户没改任何文字的情况下，把当前或离开画幅的 4 个结构段全量写进 templateText，另有 boot 恢复旧人物的自动 stash。saveState 只序列化，不生成文本。

全部写入点（快照 01:00）：

| # | 触发 | 调用链 / 行号 | 写入范围 | 用户是否改了文字 |
| --- | --- | --- | --- | --- |
| 1 | 任意块 textarea 输入 | 2011-2015 → persistBlocks（1676-1680）→ stash（1580-1587） | 当前画幅 4 结构段 | 是（哪怕改的是内容段） |
| 2 | 任意块开关 | 1983-1989 | 同上 | 否（只点开关） |
| 3 | 拖拽排序 | 2027-2034 | 同上 | 否 |
| 4 | 加/删自定义段 | 3375 附近、3386 附近 | 同上 | 是 |
| 5 | 详情预设 简洁/标准/详细 | applyDetailPreset（1260-1270）→ persistBlocks（1265） | 当前画幅 4 结构段 | 否（自动） |
| 6 | 画幅预设（8 个） | applyPreset（1773-1793）→ stash（1779） | 离开的画幅 4 结构段 | 否（自动） |
| 7 | 顶栏切换画幅 | 3521-3530 → stash（3522） | 离开的画幅 4 结构段 | 否（自动） |
| 8 | 新建画幅 | createLayout（1841-1858）→ stash（1842） | 当前画幅 4 结构段 | 否（点新建即写） |

明确没有写入的路径：boot 常规流程（3753-3767）没有 stash/persist；fillStaticSelects 里两次 loadBlocks（3761、3550 附近）只做迁移/补段/应用；saveState（114-135）仅序列化当前 templateText；migrateLegacy* 只删除/替换内存文本，不主动写新文本。两个容易误判的点：

- 「点详细度预设」看起来只改内容段开关，实际上 persistBlocks 会缓存结构段（1265 → 1676-1680）。
- 「点画幅预设」会在离开当前画幅前 stash（1779），即使你只是用预设快速切画幅，也会给旧画幅留下缓存。
- 如果用户从未做过上述任何操作，templateText 为空，data 文案更新是能正常显示的；一旦做过一次，就需要迁移或清缓存。

建议（从根本上替代 LEGACY 注册表）：stashTemplateStructure 只保存「与当前 data 默认不同」的差异：
- 若 b.text === t.structure[b.id].text 且 b.enabled === true，则 delete box[b.id]（或干脆不写）；
- 只有 text 不同或 enabled=false 才写；
- 这样 data 更新永远不会被「默认值缓存」遮住，也不需要每改一次文案就往 LEGACY_STRUCT 里加一条。
再加一个数据版本戳（templates.version + layouts hash 存 localStorage），版本变化时清掉所有与旧默认相同的缓存即可（保留真实手改）。

### 4.7 LEGACY 迁移方案的残余风险（回应 Lead 问题 2）

现状：migrateLegacyContent（1629-1635）只处理 outfit/info；migrateLegacyStructure（1653-1665）只处理 LEGACY_STRUCT 里登记的 3 个共享键 + 5 个 layout 文本（1641-1652），条件是缓存文本与旧默认「一字不差」，命中则 delete item.text（保留 enabled）。在 loadBlocks 里、applyTemplateStructure 之前执行（1667-1674）。

残余风险（按发生概率/危害排序）：

1. 部分手改导致整段不迁移（最常见）：用户只在旧版本文案末尾加了一个空格/标点/一句话，缓存文本就不再等于旧默认，迁移不会命中；结果是旧文案整段保留，data 的新文案（包括新加的机位、比例、负面约束）永远看不到。这是「全有或全无」匹配的硬伤。
2. 中间版本不迁移：LEGACY_STRUCT 只登记了「上一版出厂文案」；今天 0:41/0:44/0:45 期间改过的 intermediate 文案、以及未来再改版后的文案都不在名单。只要用户在中间版本上触发过任意 stash，就会留下一个既不是旧默认也不是新默认的缓存，之后所有迁移都匹配不上。Lead 自己的浏览器如果在这几个时间点间点过预设/切换，就可能处于这个状态。
3. 用户主动选择旧文案：如果用户就是喜欢旧文案（或把旧文案复制到别的 layout？按 tid 匹配，跨画幅复制不会命中；但同画幅复制会命中），迁移会把 text 删掉、回落到 data 新文案，且没有提示、没有撤销。命中条件越精确，这种误删概率越低，但仍然存在。
4. 注册表与 data 文案手工同步：LEGACY_CONTENT/LEGACY_STRUCT 的字符串是硬编码副本（1625-1652），与 data/templates.json 的旧值必须逐字一致；以后 data 改版时要么补登记，要么用户在旧缓存上永久卡住。维护成本会随版本线性增长，且容易漏字符/换行。
5. 只迁移 text，不迁移 label/enabled 之外的状态：label 不缓存（无影响）；但 future 若 stash 里增加其它字段（如 text 版本号），迁移逻辑不会处理。
6. 只在 loadBlocks 执行：不刷新页面就不会迁移；若用户一直开着页面，仍看到旧文案，可能误以为改动没生效。
7. 迁移后不立刻 saveState：内存里已删 text，但 localStorage 仍是旧值；下次加载会再迁移一次（幂等，无害），但如果用户在下次 saveState 前做了别的操作触发 stash，会把当前内存的 data 新文本重新写回缓存（此时等于用新默认覆盖，无损失）；若先 stash 再加载则无问题。
8. 覆盖范围窄：LEGACY_STRUCT 只登记 5 个画幅 id 的 layout 与 3 个共享键；用户新建的画幅（id=layout_xxx）、改名后的画幅、以及未来新增的模板字段都不在迁移范围。
9. 内容段同样只有 outfit/info 两条（1625-1632）；若未来改 face/body 等默认文案，没有迁移；用户改过一部分的旧内容段会永久保留旧文本（因为 blocks 是持久化的，且 migrateLegacyContent 也要求精确匹配）。
10. 无法区分「用户手改」与「旧默认」的字符串复制：最稳妥的是不缓存默认值（4.6 建议），而不是在加载时用历史常量猜。

建议：短期保留 LEGACY 作为一次性补丁，但立刻把 stash 改为 diff-only；中期用 dataVersion + 「本画幅恢复默认」按钮 + 明确的「该画幅有本地改动」徽标；长期让 layouts.json 承担画幅默认文本，localStorage 只存「用户显式覆盖」。

### 4.8 其它「改了不生效 / 显示不一致」路径（回应 Lead 问题 3）

结论：除了 templateText 缓存，最常见的还有「DATA.layouts 快照 + vars 覆盖无提示 + 切换函数重绘契约」。逐条：

1. layout.vars/suppress/orient 都读内存 DATA.layouts（buildVars 481-486、templateSuppressedIds 1528-1531、templateOrient 1544-1547），只在 boot 的 loadData 与 layout API 响应后替换（loadData 102-106、applyLayoutsResponse 1815-1824）；手改 layouts.json 不刷新 = 不生效；手改 templates.json 的 templates 数组 = 永远不生效（layouts 优先），content/order 例外。
2. 切换画幅时 renderBlocks 一定重绘吗？四条路径都重绘（3521-3530、1773-1793、1841-1858、1881-1908），boot 恢复旧人物也重绘（3785-3789）。但这是一条隐性契约：applyLayoutsResponse 自身不重绘（1815-1824），normalizeTemplate 也不重绘（1683-1688）。以后新增「切画幅」入口必须手动补 renderBlocks/renderParams/updatePromptPreview，否则会出现「下拉框/卡片显示旧画幅、提示词已是新画幅」。
3. layout.vars 覆盖参数没有 UI 反馈：usedVarKeys/updateParamUsage/offHint 不看 vars（570-577、746-766、739-744）；变量表显示覆盖值但来源仍写左栏。对用户表现为「我改了表情/视线，出图没变」。建议：参数行加「本画幅被版面改写」标记，变量表 source 显示「画幅改写」，并允许一键跳到 layouts.json 对应字段。
4. 记忆点/人物档案句子与 vars 覆盖矛盾（455-471 先于 480-486）；覆盖 expression 时，signatureSentence 仍可能是旧表情词句。建议 vars 覆盖后再生成 profileText/signatureSentence，或在覆盖时同步替换句子。
5. vars 值不递归编译（489-493），写 {{x}} 会原样进 prompt；validate 不扫描 vars 值。
6. suppress 与 negative/结构段的引用一致性无检查：grid 目前手工把 negative 改成「不要任何文字」（templates.json:202-205），但机制上若别的画幅 suppress info，它的 negative 仍可能引用左上角文字。建议 validate 增加规则：若某画幅 suppress 了 info，则该画幅 negative 文本不得包含「人物信息/文字」类断言（或至少警告）。
7. UI 无法编辑 vars/suppress/orient：只能手改 layouts.json 再刷新；新建画幅只复制 4 个结构段（structurePayload 1827-1839），不会继承 vars/suppress/orient；想复制九宫格逻辑到新画幅必须改文件。建议在画幅管理里增加「高级设置（vars/suppress/orient）」，或至少提供只读展示。
8. DATA.layouts 替换后 state.templateText 不清理：删除画幅后同 id 重建会取到旧缓存（P12）；建议删除画幅时删掉对应 templateText key。
9. applyDetailPresetFlags 每次 load 重置 4 个内容段开关（1672、1252-1258）；正常 toggle 有 markDetailCustom 保护，但旧 localStorage/手改 detailPreset 会回默认。建议只在「首次创建 blocks」和「用户点预设」时应用。
10. ensureRatioForTemplate 会在 applyTemplateStructure 里改 ratio 并 toast（1602、1552-1561）；如果在 rename/delete 当前画幅时用户已经选好比例，可能被自动改掉——这是设计，但应在 UI 上明确提示（目前有 toast，可接受）。
11. state.templateId 指向已删除画幅时 currentTemplate 回退 DATA.layouts[0]（1522-1524），此时 buildVars/suppress/filenameHint 都用第一个画幅（2736-2748），但下拉框可能还显示旧 id，直到 normalizeTemplate（1683-1688）在下次 boot 修正；会话中若手改 layouts.json 删除当前画幅则可能出现。
12. README/UI 与实现不一致：README:167 仍说界面改完「整份列表会落到 data/layouts.json」，实际结构文本编辑只存 localStorage；README:257 说存档记录提示词，01:08 后已成立（schemaVersion 3），但仍应补充 promptMeta 缺 structure/vars/suppress 快照与数据版本；README:169-177 已补 vars/suppress/orient，但没说 vars/suppress/orient 只能手改文件、刷新生效，也没给 UI 编辑入口（README:360 的 test:layouts 已补上，但没覆盖 server/persist/存档）。

### 5.1 RATIOS 与方向词的唯一来源（正常）

## 6. 其它：生成请求、存档、重试、错误处理

### 6.1 提示词实际从哪里发出去

链路（前端到上游，快照 01:00）：

1. generate（3262-3282）：检查 model、compilePrompt 非空；按张数生成 job 数组，每张 snapshotJob（2736-2758），prompt=compilePrompt()（2743）。
2. runBatch（3111 附近开始）→ streamBatch（2762-2770）：POST /api/generate-batch，body = { providerId: jobs[0].providerId, jobs }（2769）。注意只用第一个 job 的 providerId，job 里各自的 providerId 不会被服务端读取。
3. server handleGenerateBatch（server.mjs:600-618）：findProvider(body.providerId)（609）、jobs 截断到 10（612）、逐 job 校验 model/prompt 非空（614-618）、并发上限（619 附近）。
4. callUpstreamImage（server.mjs:389-394）：payload = { model, prompt, n:1, size?, quality?, output_format?, background? }（390）；prompt 原样使用，服务端没有改写、trim、截断、加前缀/后缀、也没有独立 negative_prompt 字段。
5. 请求体上限 4MB（server.mjs:608 readJsonBody(4MB)），单张 prompt 没有长度校验；空 prompt 会让整批 400（614-618）。

结论：前端 compilePrompt 是唯一 prompt 来源；服务端只是转发与重试。negative 段是拼在 prompt 文本里的普通段，不是 API 的 negative prompt 参数。

对 Lead 问题 3 的直接回答（batch 是否逐张重算 / 服务端是否截断）：

- 逐张重算：是。generate 的循环里，张数 > 1 时每张先 rerollAll（302 行起：换 seed、按锁重掷 params、重建 meta→syncAll），紧接着 snapshotJob（2736-2758）里再调用 compilePrompt()（2743），所以每张 prompt 都是「该张人物参数 + 当时 blocks」重新编译的结果。注意这 N 次 rerollAll 会在 runBatch 之前把所有 UI 重绘/保存都跑一遍（每张一次 syncAll→saveState），属于可接受的启动开销，但 10 张时会连续触发 10 次 localStorage 写入与预览重绘。
- 生成过程中改块/参数不会影响已拍快照：job 里已存 prompt/model/size/character（2736-2758）；runBatch 之后用户再改界面只影响下一批。这是对的（并发安全），但也意味着「生成中看到自己改了提示词」会误以为本批生效。
- 服务端不重算、不截断、不改写：handleGenerateBatch 只做 jobs.slice(0,10)（server.mjs:612）、逐 job 校验 model/prompt 非空（614-618）、按 jobs[0].model 取并发（620），然后每个 job 原样 Object.assign 给 callUpstreamImage（约 670 行附近）；payload 里 prompt 原样（388-393），重试循环也不改 payload（同一 prompt 重发）。请求体上限 4MB（609），单条 prompt 无长度上限；空 prompt 会让整批 400。
- 一个容易忽略的点：服务端只用 body.providerId（610），每个 job 里的 providerId 被忽略；model/size/quality/prompt 用 job 自己的。前端每批只有一个 provider，所以现在没问题；但「重试旧 job」时 providerId 仍是旧值（6.3）。
- 并发上限只按 jobs[0].model 计算（620）；如果以后允许一批混多个模型，并发限制会不准。

管线层其它漏项（Lead 问题 3 的补充）：

1. 服务端会「静默截断任务数」：jobs.slice(0,10)（server.mjs:612）。前端 batchLimit 也是 1-10，所以从 UI 无感；但 API 层面第 11 个 job 会被无声丢弃，不报错、不提示。若以后允许 >10 或外部脚本调用，应该显式 400 而不是 slice。
2. 重试次数口径不一致：前端 snapshotJob 固定 retries:3（app.js:2746），server 用 Math.max(1, Math.min(4, Number(body.retries) || 3))（server.mjs:399）→ 实际最多 3 次尝试；而 RETRY_DELAYS_MS 有 3 个退避值（1.5s/4s/10s，server.mjs:373-375），3 次尝试只会用到前 2 个退避。README:216-217 写「最多 4 次」与实际不符（或者前端应传 4）。这是「重试策略看起来生效、实际少一次」的典型。
3. 上游返回多图时只取第一张：callUpstreamImage 固定 payload.n=1（server.mjs:390），并从 j.data[0] 取图（server.mjs:440-441）；若上游忽略了 n 返回多张，其余被丢弃。对当前需求没问题，但存档/计费口径会与上游不一致。
4. 请求体总量限制会变成「整批失败」：readJsonBody(req, 4MB)（server.mjs:609）；10 张 prompt 总量超 4MB（例如用户把大段文字粘进内容段）会整批 400，而不是单张失败。客户端预算只提示 1800/2100 字，不阻止超长；服务端也没有单条 prompt 上限。
5. per-job providerId 被忽略：body.providerId 是批次级（server.mjs:610），job 里的 providerId 不参与；当前前端每批只有一个 provider，无影响，但重试旧 job 时会暴露（6.3）。
6. 批次快照不含 prompt：batchSnapshot 有意排除 prompt（server.mjs:111-130），所以刷新/接管后无法从服务端拿回失败 job 的 prompt；这与 6.3 的重试丢失是同一个根因。
7. compilePrompt 在 generate 循环里被调用 N 次 + 一次空提示词检查（3268、2743）；每次都 buildVars 全量参数 + 复制 blocks，10 张时有重复计算，但相对于出图耗时可忽略，不是瓶颈。
8. rerollAll 每次 syncAll→saveState（301-317）：10 张会在生成开始前连续写 10 次 localStorage，并触发 10 次 renderParams/updatePromptPreview；如果 localStorage 不稳定/慢，用户会看到生成按钮点击后界面卡顿，但 job 快照本身已经拍好，不影响正确性。

### 6.3 失败重试会用旧提示词/旧服务商

结论：重试用 failedJobs 里的 job 快照（含旧 prompt、旧 model、旧 providerId），这是「原提示词重试」的设计，但实现没有区分「用户已换服务商/模型/数据」的情况，容易用错；且刷新后 failedJobs 丢，无法重试。

证据：

- failedJobs 是内存变量（app.js:2823）；只有批次正常结束（reason !== stopped）才把失败 job 快照写入（app.js 3191-3201 附近）。
- retryFailed（3285-3294 附近）取 failedJobs.slice() 后 runBatch；job 快照里的 providerId/model/prompt/size/character 都是生成时捕获的（2736-2758）。
- streamBatch 只用 jobs[0].providerId（2769）；服务端 handleGenerateBatch 用 body.providerId（609）。如果用户在失败后切换了服务商（或删除了旧服务商），重试仍然发往旧 provider，可能 400「未找到该服务商」或静默用旧服务商。
- 刷新页面后 takeoverActiveBatch 只恢复「进行中」的批次进度（3086-3116 附近），不恢复失败 job 列表；updateRetryButton 依赖 failedJobs（2825 附近），刷新后不会出现重试按钮。
- 用户改了提示词/画幅/vars 后再点重试，仍是旧 prompt（符合 README 213 的「原提示词」语义），但 UI 没有展示「将重发哪一版 prompt」，也没有「用当前提示词重试」的选项。

建议：

- 重试时重新解析当前 provider（按 providerId 找不到就明确提示并要求选择），或直接把旧 job 的 providerId 在 UI 展示；model 同理。
- failedJobs 持久化到内存之外的 sessionStorage/localStorage（只存 idx/prompt/provider/model/character），刷新后可恢复；或至少把失败信息写入存档 index，提供「从存档重试」。
- retry 前显示即将发送的 prompt 摘要/字数/画幅，并给「用当前提示词重试」的第二个按钮。

### 6.4 错误处理与批次收尾

- 批次级错误：任一 job 缺 model/prompt 会让整批 400（server.mjs:614-618）；前端 streamBatch 把非 2xx 解析成 Error（2762 附近），runBatch catch 后 finalizeBatch。整批失败时用户能重试吗？取决于是否已生成失败 job 快照（批次没开始就不会有 failedJobs）。
- job 级错误：job-done 分支把失败写入 failures 并设置 state.lastError（app.js 3160-3163 附近），但 lastError 用的是 jobs[0].model，即使失败的是别的 job（当前同批同模型，影响小）。
- 停止（cancel）：只停止派发新任务；已取消的 job 不进 failedJobs（3191-3201 只在 reason!=stopped 时赋值），所以停止后不能「重试」这些未开始的 job，只能重新生成（人物会重新随机）。
- /api/generate 单张接口仍存在（server.mjs:470、1199 路由），但前端只用 generate-batch（app.js 只有 2766 的 /api/generate-batch）；单张接口是死路径，长期会与批量逻辑漂移。
- 批次注册表只在内存（server.mjs batches），服务重启丢失；README 已说明。存档在服务端串行锁内完成（withIndexLock 471-483 附近），编号安全。

### 6.5 附带发现（非本次六项，但高风险）：/data/ 路径穿越（01:15 后已修，保留记录）

状态：Lead ① 已在 01:15 前后把 /data、/files、静态资源的路径全部改为 resolve + 前缀校验，并用 4 条 %2e%2e%2f 请求实测返回 403。本节保留原始发现与修复建议，作为安全基线记录；建议补一条自动化测试（例如 scripts/test-paths.mjs 或 test-batch 里加 4 条断言），防止以后重构路由时回归。

原始结论（修复前）：server.mjs:1229-1240 的 /data/ 静态文件路由只做 path.join(DATA, decodeURIComponent(pathname.slice(6)))，没有 resolve + 前缀校验；用 %2e%2e%2f 编码可绕过 URL 规范化的点段折叠，读到项目根目录文件（包括 config.json，内含明文 API Key）。本机 127.0.0.1 + 全局 CORS（server.mjs:1096-1099 设置 Access-Control-Allow-Origin: *）下，浏览器里的任意页面理论上可跨源读取。

建议：该路由改为 const rel = decodeURIComponent(...); const target = path.resolve(DATA, rel); if (!target.startsWith(path.resolve(DATA) + path.sep)) return 403; 并把 config.json 等敏感文件移出可访问目录。此项超出画幅管线范围，但建议尽快单独修。

### 7.2 推荐的数据结构（JSON 形状）

在 layout 对象上增加 content 覆盖（templates.json#templates[i] 与 layouts.json#layouts[i] 同构）：

    {
      "id": "portrait",
      "label": "半身肖像",
      "orient": "portrait",
      "structure": { "format": {...}, "layout": {...}, "style": {...}, "negative": {...} },
      "vars": { "outfitExtra": "；本画幅只到胸口下沿，不出现腰、腹、胯、腿、脚与下身衣物" },
      "suppress": ["info"],
      "content": {
        "body": { "text": "体型：{{bodyBuild}}。{{frameWidth}}。{{muscle}}。{{shoulder}}，{{hip}}，{{neck}}。{{chest}}。{{larynx}}。{{bodyHair}}。", "enabled": true },
        "proportion": { "enabled": false }
      }
    }

语义建议：suppress 优先（整段不拼）；content[id].enabled=false 等价「本画幅关闭」；content[id].text 覆盖全局文本；vars 仍只覆盖变量值；编译顺序：effective text → buildVars（含 layout.vars）→ 替换。content 只允许内容段 id（与 suppress 相同集合），结构段仍放 structure，避免与 server LAYOUT_KEYS 冲突。

可选加 order（按画幅顺序）：

    "order": ["format", "layout", "subject", "...", "info", "negative"]

不写则沿用全局 state.blocks 顺序。实现时按 id 过滤/补漏，未知 id 忽略并在 validate 报错。
